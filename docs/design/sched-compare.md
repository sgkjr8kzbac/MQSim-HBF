# 请求调度对比报告：简化调度器 vs ServeLoop（vLLM 0.26 FCFS）

> **目的**：在同一批真实 Mooncake 请求上，对比本仓库简化调度器（[`hbf/lifetime/sim/engine.py`](../../hbf/lifetime/sim/engine.py)、[`ops.py`](../../hbf/lifetime/sim/ops.py) 与 [`hbf/frontend/timeline.py`](../../hbf/frontend/timeline.py)）与 [ServeLoop](https://github.com/FlashLabAE/ServeLoop)（固定提交 `7d5d7a4`，MIT 许可）的行为差异，判断简化调度对 HBF 寿命与写入特征评估是否够用。  
> **范围约束**：本次仅做测试、复现与汇报，**不修改**核心 `hbf/` 调度逻辑、黄金文件或 MQSim 行为。  
> **数据与脚本**：请求转换器 [`scripts/mooncake_to_serveloop.py`](../../scripts/mooncake_to_serveloop.py)、对比脚本 [`scripts/sched_compare.py`](../../scripts/sched_compare.py)、完整指标表 [`evidence/sched-compare.csv`](../../evidence/sched-compare.csv)、ServeLoop 固定提交 [`hbf/serveloop.commit`](../../hbf/serveloop.commit) 与拉取脚本 [`scripts/serveloop_build.sh`](../../scripts/serveloop_build.sh)。

## 1. 总结论（先看判定）

按初定的三条判定标准（① 批大小中位数差 ≤ 10%；② 抢占重算写入 ≤ 总 KV 写入 5%；③ 每天 P/E 次数差 ≤ 5%）：

- **总体判定：不满足全部标准，简化调度不能无条件替代 vLLM 式调度。** 8 组核心对照中 **0 组** 同时通过三条标准。
- **有条件够用的场景（容量充足 + 无前缀共享，单看写入总量与寿命）**：在 512 GiB 充足容量、无前缀共享下，两者的 KV 总写入仅差 **+0.05%**（`2,202.8` vs `2,203.8 GB`），抢占重算均为 **0.0%**，按活动跨度折算的日均 P/E 差为 **−0.56%**（对齐计时，`X=1e5`）和 **−4.45%**（默认计时，`X=1e5`），均通过 ≤ 5% 标准；即便改按稳态到达窗（`1,155 s`）折算，无读干扰（`X=1e6`）下日均 P/E 仅差 **+0.1%**。因此**仅估算无前缀、无抢占、容量充足工况的 HBF 擦写寿命时，简化调度够用**。
- **明显失真的场景与四大主因（按影响排序）**：
  1. **分块 prefill 与 token 预算混批（主导批大小、延迟与 1 s 写入突发）**：即使把 ServeLoop 每步耗时对齐到我方 B200+HBF 时钟，我方整段串行 prefill 仍令 decode 周期性停顿，E2E P50 延迟偏高 **2.5×**（`111.4 s` vs `45.0 s`），由 Little 定律推高在跑批大小中位数 **+45.8%**（`35` vs `24`；开前缀后达 **+260%**，`36` vs `10`），1 s 写入峰均比偏高 **3.2×**（`13.5` vs `4.2`）。
  2. **容量紧张下的分配粒度（1 GiB 超块 vs 2 MiB 分页）与压缩放大**：在 `120 GiB` 紧容量下，我方 1 GiB 超块在低水位回收时产生严重的活页搬移写放大，日均 P/E 飙升至 `6,595–8,156`，比 ServeLoop 高出 **+244% 至 +381%**（且容量低于 ~112 GiB 时我方因 1 GiB 超块耗尽而报错）；而在 ServeLoop 侧，2 MiB 细粒度分页把容量压榨到近 100% 后再触发抢占，一旦将此调度重放到 1 GiB 超块磨损模型上，同样触发约 9× 压缩写放大（`13,122 PEC/d`）。
  3. **最晚请求抢占 + 重算写入悬崖**：我方采用“空间不足即排队等待、零抢占”策略，重算恒为 0；ServeLoop 在 `120 GiB` 对齐计时下出现 **143 次抢占 / 4.61% 重算**，进一步压到 `64 GiB`（对齐计时）和 `24 GiB`（默认计时）时发生严重的抢占震荡——抢占达 **6,937 / 21,522 次**，重算占总 KV 写入 **65.3% / 85.5%**，总 KV 写入暴涨 **2.9× / 6.9×**。若启用 ServeLoop 的 HBF 冷层换出（`64 GiB HBM 热 + 512 GiB HBF 冷`），385 次抢占全部转为冷换出（`314.7 GB`），重算重新归零。
  4. **细粒度前缀缓存（16 token 块）vs 粗粒度单组前缀**：在 `X=1e5` 强读干扰下，即使总 KV 写入相近（`1,648` vs `1,632 GB`，差 `+1.0%`），我方单组前缀 + 高并发把读干扰集中在少数前缀段上（`ref/kv = 0.76` vs ServeLoop `0.36`），导致 `X=1e5` 日均 P/E 偏高 **+24.7% 至 +30.8%**；在 `120 GiB` 紧容量下，ServeLoop 的 16-token LRU 命中率（`13.3%`）也显著高于我方粗粒度单组前缀（`8.3%`）。

## 2. 实验设置与对齐说明（如实记录差异）

### 2.1 外部依赖与版本固定

- **ServeLoop**：未纳入仓库；通过 [`scripts/serveloop_build.sh`](../../scripts/serveloop_build.sh) 克隆至 `.build/serveloop/7d5d7a4b767d`，提交号固定在 [`hbf/serveloop.commit`](../../hbf/serveloop.commit)（`7d5d7a4b767d131225cd93bb6f8056f4ef67b278`，2026-10-31）。
- **HBFSim**：复用现有 [`scripts/hbfsim_build.sh`](../../scripts/hbfsim_build.sh)（固定提交 `8ab183cc5117`），经校验与 ServeLoop `7d5d7a4` 内置 `hbfsim_client` 完全兼容。
- **ServeLoop 上游缺陷记录（不改上游源码）**：运行紧容量抢占场景时，发现 ServeLoop `7d5d7a4` 的 `serveloop/engine.py:258-262` 存在二次抢占缺陷——当已输出 `emitted >= 1` 个 token 的请求在重算未完成前被再次抢占时，上游将 `state.prefill_target` 错误重置为 `prompt_tokens` 而丢弃已输出的 `emitted` 个 token，触发 `ServeLoopError: decode frontier is inconsistent`。我们在评测脚本 [`scripts/sched_compare.py`](../../scripts/sched_compare.py) 中用 4 行子类 `FixedPreemptEngine` 将 `prefill_target` 设为 `prompt_tokens + state.emitted` 予以局部修正。此外，上游 `PrefixCache.expire()` 每轮线性扫描全部 ~10 万条条目导致前缀实验耗时 >15 min，脚本中用等价最小堆 `FastExpirePrefixCache`（不改变任何驱逐/过期顺序）将其加速到 ~2 min。

### 2.3 KV 放置在 HBF 上的模型差异（重点如实说明）

检查 `serveloop/placement.py:59, 98-99` 可知，ServeLoop **硬编码禁止热/在跑 KV 驻留 HBF**：

```python
if self.hot != "hbm":
    raise ServeLoopError("hot KV must live in hbm")
```

其内置放置预设只有三种：
- `all-hbm`：权重在 HBM，热 KV 在 HBM，抢占后**重算**；
- `weights-hbf-kv-hbm`：权重在 HBF，热 KV 在 HBM，抢占后**重算**；
- `weights-hbf-kv-hbf-cold`：权重在 HBF，热 KV 在 HBM，被抢占的冷 KV **换出到 HBF**（不重算）。

这与本仓库“**权重在 HBM、全部 KV 直接驻留 HBF**”的假设存在本质差别：
1. 为实现单层 KV 池 + 权重在 HBM + 抢占重算 + 前缀缓存的对照，8 组核心实验在 ServeLoop 侧采用 `all-hbm` 放置（将 HBM KV 池精确配置为 `512 GiB` / `120 GiB`，前缀缓存共享同一 KV 池），并通过**对齐计时**将 HBF 读延迟反馈回 ServeLoop 的每步时长；
2. 另设诊断场景 `tight_64g_hbf_cold`（权重 HBM、`64 GiB` HBM 热 KV + `512 GiB` HBF 冷 KV 换出，使用 `4hbm-4hbf.cfg` 的 `hbf_geometry`），专门考察 ServeLoop 冷层换出模式对重算与 HBF 写入的影响。

### 2.4 计时对齐与 HBFSim 校准

- **我方默认计时**：`ext/system` 的 B200 + 1-stack OCP HBF TPOT 时钟（`read_ns=4096`，`overlap="serial"`，`kv_consume="stream"`，`prefill="colocated"`）。
- **ServeLoop 默认计时**：H100 `RooflineTimingProvider(peak_tflops=989.0, efficiency=0.6)` + `4hbm-4hbf.cfg` HBM4 带宽（4 stack × 32 ch × 2 pc × 4 B × 8 GT/s × 0.94 = `7,700.48 GB/s`）。因 14 万步全量调用真实 `HbfSimExecutor`（`all-hbm` ~110 ms/步，约 4.3 h；`weights-hbf-kv-hbm` ~3.0 s/步，约 84 h）过慢，我们在 6 条真实 Mooncake 请求（32 轮迭代）上将解析步时与真实 `HbfSimExecutor` 做了直接校准：

| 迭代类型 | 样本轮数 | 真实 `HbfSimExecutor` 均值 (ms) | 解析模型均值 (ms) | 相对误差 |
|---|---:|---:|---:|---:|
| `prefill` | 4 | 173.148 | 173.053 | **−0.05%** |
| `mixed` | 9 | 148.420 | 148.233 | **−0.13%** |
| `decode` | 19 | 1.977 | 2.045 | **+3.44%** |

- **ServeLoop 对齐计时（`matched`）**：在每轮迭代中，将当前 batch 内所有 decode slice 送入我方同一个 B200+HBF `tpot` 时钟，加上当前 batch 内 prefill token 按我方 `resolve_prefill_tok_s` 计算的 prefill 耗时，从而在尽可能接近的步时尺度下隔离“纯调度规则差异”。

### 2.5 ServeLoop 调度结果重放到我方 HBF 寿命模型的方法

`scripts/sched_compare.py` 中的 `replay_serveloop_on_hbf_wear` 捕获 ServeLoop 每轮迭代的精确事件流——被抢占请求释放、前缀缓存驱逐/过期页数、每请求新写入 token（区分私有 KV 与新发布前缀块）、每条 slice 读取的上下文页数与命中前缀页数、完成请求释放——并严格按我方 `hbf/lifetime/sim/` 的 1 GiB 超块（`1,024 bank × 256 page/bank = 262,144 page`）打包段、低水位贪心回收与读干扰（`X=1e5`、`X=1e6`）重搬移规则计算 `PEC/day` 与 `refresh_to_kv`。**全部 11 组 ServeLoop 场景均在同一 1 GiB 超块模型上完整收敛（`wear_status = ok`）**。  
*注*：`replay_serveloop_on_hbf_wear` 中的 `refresh_to_kv` 统计 `(读干扰搬移 + 空间压缩搬移) / KV 写入`，而我方 `Simulator` 的 `refresh_to_kv` 仅统计 `读干扰搬移 / KV 写入`（压缩写放大体现在 `PEC/day` 中，不计入 `refresh_to_kv`）；下文解读紧容量 `refresh_to_kv` 时已明确区分。

## 5. 差异根因拆解与对后续演进的建议

1. **分块 prefill 与混批（影响最广：所有 8 组场景）**
   - 我方每接纳一条请求就串行跑完整段 prompt（最大 113,700 token），期间所有在跑 decode 停顿；Mooncake 重尾长 prompt 导致单次 prefill 停顿长达数秒，既拉高 1 s 写入尖峰（`peak/mean = 13.5` vs `4.2`），又通过排队长尾将稳态批大小拉高 1.5–3.6×。
   - **何时影响结论**：若只关心 10 s 以上时间尺度的写入均值或充足容量无前缀 P/E，影响很小；但若要评估 **TPOT 尾延迟、并发批大小分布、或写入干扰（瞬时写突发对读尾延迟的冲击）**，整段串行 prefill 明显失真。

2. **分配粒度（1 GiB 超块 vs 2 MiB 分页）与紧容量压缩写放大**
   - 我方段级回收以 1 GiB 超块为单元，在 512 GiB 充足容量下占用率 < 30%，几乎无压缩放大；但在 120 GiB 高占用下，大量长短不一的请求交错驻留同一超块，回收写放大高达 **6.3×**（更低容量甚至触发 `No free segment`）。
   - 同时，把 ServeLoop 2 MiB 分页高占用调度直接重放到 1 GiB 超块上同样出现 **9.1×** 压缩放大——这说明对紧容量 HBF 寿命而言，**段/擦除块管理粒度（或按寿命/请求分组隔离）与请求调度同等重要**。

3. **抢占重算 vs 排队等待**
   - 我方“空间不够就排队、永不抢占”在紧容量下避免了 KV 写入放大（总写恒为 `2,202.8 GB`），但代价是极高的 E2E 延迟（`209.5 s` vs `48.0 s`）。
   - ServeLoop 遵循 vLLM 0.26 抢占最晚在跑请求并重算：在 `120 GiB` 临界点仅增加 **4.6%** 写入，但越过拐点进入 `64 GiB / 24 GiB` 后会出现 **65%–85% 的重算雪崩**，彻底主导擦写寿命。如果目标系统使用 vLLM 抢占且 KV 池接近饱和，简化调度会严重低估写入量与磨损；反之若系统配置了 HBM 热 + HBF 冷换出（`tight_64g_hbf_cold`）或足够大的单 stack 容量（512 GiB），则不会落入重算雪崩区。

4. **前缀缓存粒度（16-token 块 vs 单组前缀）**
   - 在无读干扰（`X=1e6`）与充足容量下，两者总 KV 写入差仅 **1.0%**，日均 P/E 差 **−3.3% 至 −3.7%**（通过 ≤5%）。
   - 但在强读干扰（`X=1e5`）下，我方粗粒度单组前缀叠加高并发造成 **+24.7% 至 +30.8%** 的 P/E 偏高；紧容量下我方整组驱逐也让前缀命中率低于 ServeLoop（`8.3%` vs `13.3%`）。

### 结论与待决策方向

- **若当前阶段仅关注“容量充足（512 GiB）、无前缀或弱读干扰（`X=1e6`）下的稳态 HBF 擦写寿命估算”**：现有简化调度器的总 KV 写入（误差 < 1%）与稳态日均 P/E（误差 < 5%）**基本够用**，无需急于大改核心调度。
- **若后续研究需要覆盖“紧容量（抢占重算）、瞬时 1 s 写入突发与读尾延迟、准确批大小/E2E 延迟分布、或 `X=1e5` 强读干扰下的细粒度前缀缓存”**：则需在两条路线中择一推进（本次按约束暂停实现，待确认）：
  - **方案 A**：在 `hbf/frontend/timeline.py` 与 `hbf/lifetime/sim/` 中引入轻量 vLLM 规则（token 预算分块 prefill + 可选抢占重算/排队开关）；
  - **方案 B**：保持核心仿真器简洁，新增外部调度导入器，直接消费 ServeLoop 输出的每轮调度日志驱动我方 HBF 寿命与介质仿真后端。
